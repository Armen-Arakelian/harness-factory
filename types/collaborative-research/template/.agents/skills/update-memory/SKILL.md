# Update Research Memory

The project root is three directories above this skill folder. Read its `rules.md` and resolve paths from that root.

For each new or revised preview, read `../memory-approval/SKILL.md` before presenting it. With `visualize` available, the initial response must contain the approval card, rather than a text-only question. Do not repeat the preview outside the card. Approval is required by the project rules; this skill implements that existing choice, not an additional permission step.

1. Identify the requested change. Search candidate filenames, titles and bounded content matches in the relevant `nodes/`, `details/` or `people/` folder, using useful synonyms or aliases. Read the closest candidates and relevant map entries; follow useful detail links only when needed to establish what is already recorded. Do not load the whole vault for each save. Choose creation, update or no change using the section below. The user must initiate changes to existing conclusions; never add conclusion maintenance to an information save. For rename or deletion, inspect incoming links.
2. Choose `nodes/` for short information, `people/` for a person, or `details/` for deeper curated explanation. For a person, follow the People section of `rules.md`: deduplicate against people and information notes, establish personal-access status from supplied evidence, and preview the complete substantive note including canonical `contact_status` frontmatter. Status edits use the complete replacement substantive note, not an isolated body fragment. Use `kind: person` for a single people save; use `kind: batch` for two or more substantive note changes, including mixed people/information/details. Requested mixed maintenance may use `maintenance`. Apply Information Notes and Details in `rules.md` to each information note, including existing dedicated details; include useful depth in the proposed save rather than discarding it. Follow note shapes and keep substantive content separate from connection sections.
3. Show a short preview: the destination/title and exact information to save, or the substantive edits to an existing note. State requested renames/deletions explicitly. Do not enumerate connections, reverse-link files or README link edits unless the user asks. If a batch contains substantive changes to multiple notes, preview each. Temporary previews may go in `work/`; do not write curated memory yet.
4. Use `../memory-approval/SKILL.md` to register this exact preview and present buttons when supported, otherwise a concise text approval. A save request starts the preview, not the write. Only an accepted ID check authorizes the returned content; rejection, silence or an intervening ordinary message means no write. Re-preview changes to meaning, wording, scope or destination. Do not ask again for content just accepted by the helper.
5. After approval, save that content and choose relevant connections under `rules.md`. For people, link to specific contributions, active questions or existing thoughts about them; exclude links justified only by their employer or broad field. Explain what makes each selected connection useful. Maintain necessary reverse links and README discovery entries automatically as part of this save. Use existing targets or notes whose content was approved in the same batch. These mechanical edits require no separate link approval; they must not change unrelated prose, create unapproved notes, invent evidence or prune unrelated connections. Show link details only on request or when a relationship would change the approved meaning.
6. Recheck affected files before applying edits and preserve intervening work. Re-preview substantive conflicts; recompute link-only edits against the latest files without overwriting content. Verify the saved text and changed links. After a successful substantive create or edit in `nodes/` or `details/`, use `../manage-glossary/SKILL.md` if `glossary.md` exists and is enabled, passing only those substantively saved files and the details saved in this operation. Exclude reverse-link-only edits, renames/deletions without new information, people-note-only saves, conclusions and README changes. A glossary failure leaves the approved research save intact; report it briefly without repeating the save. Then give a brief confirmation. Do not modify settings or instructions incidentally.

## Select a Useful Batch

A document, research result, conversation, source collection or other material can justify several notes. The user need not request each one separately: when saving is requested, or when suggesting a significant reusable result, propose one coherent package if distinct useful entries warrant it. A research request alone does not authorize writes. Do not append batch proposals to every reply.

Choose creation, update or no change for each candidate using the section below. Prefer a small coherent set over a catalogue: each short note should have independent retrieval value. Do not make one file per paragraph, every named person or every source mention. No fixed note quota applies. A package can contain a person and two informational notes, several informational notes, supporting details, or a mixture of creations and updates. Do not invent content merely to fill a package. New conclusions still require the user's initiation and their own content preparation through `create-conclusion`; never derive them unsolicited from source material.

Choose dedicated, existing, justified shared or no details separately for each information note under `rules.md`; saving several notes together is no reason to use one catch-all detail or omit available depth. A short note plus its substantive detail creation/edit also uses one batch, with each file shown; never hide detail content among delegated link edits.

Use one `batch` preview with a descriptive package title and one `changes` entry for each substantive file change. Show each destination, create/update action and exact short content or changed passage; people retain the full substantive note and status. All entries share one ID and one Approve/Cancel pair. Keep connection choices out of the preview unless requested; useful links can connect existing notes and approved entries within the package, but shared source material alone does not justify every possible connection.

An approval covers exactly the displayed package. A request to remove, add or revise an item expires the old proposal under the normal turn rules; register and show the revised whole package rather than applying a subset of an old approval. Do not ask for approval separately for each displayed entry or silently add another substantive change after acceptance.

Before the first write, reread all target files and check expected create/edit actions. A substantive conflict in any target requires a fresh package preview before writing the rest. Apply substantive changes, then delegated links only to targets that actually exist, preserving unrelated text. Verify the written package. If a write fails partway, report the actual saved and unsaved entries; do not claim complete success, blindly rewrite successful entries or promise transactional rollback. Follow the existing fresh-preview rules for a further attempt on the remaining changes.

Maintain the glossary once for the successfully saved substantive `nodes/` and `details/` in this operation, excluding people and reverse-link-only files; do not run a full-project scan or one redundant glossary pass per note. An unchanged candidate does not need a write or inclusion in the package.

## Choose Creation, Update or No Change

A request to save information does not inherently request a new file. Choose before preparing the preview:

- **Update:** the same subject and compatible scope are already recorded, and the new material adds a useful fact, qualification, source or correction. Reuse the stable path. Preserve relevant existing information, uncertainty, sources and links; change only the affected passage. Do not overwrite the note with just the newest fragment or repeatedly append the same point.
- **Create:** the information has a distinct subject, meaning or independently useful scope that deserves its own short entry. A shared keyword or employer is not enough to combine subjects. If supporting material is too long for a short node, propose an appropriate detail creation/update instead of an oversized node; do not move old content without previewing that substantive change.
- **No change:** the meaning and useful supporting material are already saved. Point to the existing note and explain briefly; create no redundant preview, note or link churn. The same claim with a materially useful new source can still warrant an update.

When new evidence conflicts with a saved informational claim, identify the conflict and preview the exact correction or scoped qualification with its evidence basis. Do not silently replace it, erase still-relevant caveats or merge incompatible statements as settled fact. Conclusions remain user-owned and are not revised as a side effect.

The preview identifies **Create** or **Update** and its destination. For ordinary note edits, show the exact added/replacement passage and enough context to locate it, explicitly naming removed claims where applicable; omit unrelated unchanged content. People edits retain the complete substantive-note preview required above. Approval covers that precise edit, not a general rewrite. If two existing notes are plausible homes and the choice materially changes meaning, clarify; otherwise choose and explain the destination in the preview. Respect an explicit request for a separate note, while briefly pointing out a likely duplicate when useful.

This workflow does not autonomously consolidate, rename or delete old notes. Such operations need a separate requested scope and explicit preview. Recheck the chosen note before writing; substantive intervening changes require a fresh preview. An update to a current saved information node/details uses the existing bounded glossary hook just like a creation; no unrelated-note scan is added.

Occasionally suggest saving significant reusable information or details; never initiate a user conclusion or append save proposals to every reply.
