# Save Factory through a Pull Request

Resolve the Factory root three directories above this skill folder. Run Git there, never in an ancestor repository. Read `../update-factory/SKILL.md` and complete its Publication Check before committing or publishing. Reuse valid current evidence; report missing or failed checks honestly. This workflow is Factory-only; generated projects retain their own backup skills.

1. A request to save, push or publish Factory authorizes committing the intended changes, pushing a task branch and opening or updating its PR. It does not authorize merging, enabling auto-merge, bypassing branch rules or pushing to `main`. Honor narrower requests such as commit-only. Do not publish automatically after development.
2. Verify the Git root, current branch, status, fetch/push URLs and default branch. Use `setup-git` only for requested initial repository setup. Clarify an unexpected destination before upload. Fetch the remote and inspect existing work and outgoing commits. Work on a branch for this task; continue a matching existing PR rather than creating a duplicate. If changes were made on `main`, move only the intended task onto a new branch without discarding or uploading unrelated work. Do not switch a shared checkout while another task is using it; use a separate worktree for concurrent tasks.
3. Inspect changed, staged and untracked paths and relevant diffs. Honor `.gitignore`; exclude personal configuration, credentials, temporary output and Obsidian workspace state. If such files are tracked/staged, stop and report them without printing secrets. Do not force-add ignored files, rewrite research memory or invent a Git identity.
4. Stage the intended changes and check the staged diff and `git diff --cached --check`. Commit with a concise English message; skip an empty commit. Include only changes within the task. Complete the Publication Check for the entire diff against the remote default branch, including existing outgoing commits. Run relevant checks and ensure user documentation matches behavior.
5. Push explicitly to `origin <task-branch>` with upstream tracking as needed, never to the default branch. Do not force push, reset, auto-stash or silently merge/rebase to get past a rejection. Resolve a failed or non-fast-forward push within the requested scope; a local commit alone is not a remote backup. Verify the remote task-branch hash matches HEAD.
6. Open or update a PR targeting the default branch, with an English description of the problem, resulting behavior and validation. Use a body file with `gh` for multiline descriptions. Attach every created PR to the current chat with the app's attachment tool when available. Check CI and report the PR URL, branch/commit, results and any remaining uncommitted changes. An open PR means the changes are uploaded but are not yet in `main`.
7. Merge only when the user explicitly requests it. Recheck the current PR diff, head commit, base, conflicts and required CI; honor repository rules and do not use admin bypass. If the PR changed materially since the user's review, surface that change before merging. Report the resulting merged commit. Otherwise leave the PR open; do not enable auto-merge.

This workflow does not authorize repository visibility changes, new research content, settings changes outside the requested task or deletion of temporary files. Branch protection is a GitHub setting; do not disable it to complete a save.
